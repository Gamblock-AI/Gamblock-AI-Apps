# Flutter Distribution and Build Matrix

This document is the canonical implementation context for the Android and
Windows variants produced by this repository. The PKM proposal remains the
authority for product intent; this matrix records how that intent is packaged
under each platform's distribution boundary.

Diagnostic artifacts are never presented as signed, store-ready, or
production-ready. They remain short-retention GitHub Actions artifacts and are
not linked from the website or handed to research participants.

## Build configuration

The Flutter client bundles only public configuration in `.env`:

```text
APP_ENV=ci|development|production
API_BASE_URL=<backend origin>
WEB_BASE_URL=<website origin>
```

Diagnostic CI uses loopback fixture origins and does not require a backend,
keystore, Authenticode certificate, or private grant-signing key. The native
grant trust store may be empty in diagnostic builds; native grant verification
then fails closed. Research Staging is different: both its Android and Windows
jobs require `PROTECTION_GRANT_TRUST_STORE_BASE64`, validate that base64 decodes
to a non-empty JSON object with non-empty DER P-256 public-key values, and pass the public map
into the native builds. No private grant-signing material enters either client.

Signed builds require the following protected inputs:

| Input | Scope | Secret? |
|---|---|---|
| `PLAY_KEYSTORE_PATH`, `PLAY_KEYSTORE_PASSWORD`, `PLAY_KEY_PASSWORD` | Play AAB | Yes |
| `RESEARCH_KEYSTORE_PATH`, `RESEARCH_KEYSTORE_PASSWORD`, `RESEARCH_KEY_PASSWORD` | Research APK | Yes |
| `ANDROID_PLAY_KEY_ALIAS`, `ANDROID_RESEARCH_KEY_ALIAS` | Android key aliases | No; GitHub Variables |
| `WINDOWS_PILOT_SIGNING_PFX_BASE64`, `WINDOWS_PILOT_SIGNING_PFX_PASSWORD` | Windows pilot MSI (production + staging) | Yes |
| `WINDOWS_TIMESTAMP_URL` | Windows pilot timestamp endpoint | No; optional GitHub Variable |
| `PROTECTION_GRANT_TRUST_STORE_BASE64` | Android/Windows native verifier | No; public key map |
| backend `PROTECTION_GRANT_SIGNING_PRIVATE_KEY` | Backend only | Yes; never copied to Flutter |

The Windows `pilot-signing` environment holds the Authenticode PFX. For the
staging release lane the PFX is the owner-generated self-signed certificate, so
staging MSIs still trigger SmartScreen/Defender warnings; a production CA-issued
code-signing certificate is required before public pilot distribution.

Signing identities are independent. A Play key, Research key, Windows
certificate, and backend ES256 key must never be reused for another purpose.

## Versioning and artifact naming

`pubspec.yaml` is the local fallback version. CI overrides the version at build
time:

- diagnostic builds use `0.0.0-ci` plus the GitHub run number;
- signed builds use the immutable `vMAJOR.MINOR.PATCH` tag and the run number as
  the Android/Windows build number;
- every artifact name includes its variant, version, and commit/run identity;
- no workflow creates or mutates a `latest` artifact.

## Workflow contract

- Pull requests and `main` run verification and diagnostic builds without
  production secrets.
- Diagnostic output is uploaded only through `actions/upload-artifact` with a
  short retention period.
- The `Signed Release Candidates` workflow (`release.yml`) runs from an
  immutable `vMAJOR.MINOR.PATCH` tag or a manual `workflow_dispatch` with the
  same semver input; it builds the signed Play AAB, Research APK, and Windows
  pilot MSI and fails closed when any required key or trust value is absent.
- The `Research Staging Release` workflow (`staging-release.yml`) is a manual
  `workflow_dispatch` that publishes the research staging APK and the Windows
  staging pilot MSI (staging backend, self-signed PFX) to a GitHub Release for
  QA/test. Both jobs fail before compilation when the public grant trust store
  is missing, malformed, or empty; the workflow never consumes the backend
  private signing key and never touches the signed release lane.
- Store publication, pilot handoff, and device/VM evidence remain external
  approval gates.

## Evidence status

Successful CI compilation proves only that the selected source set and
packaging inputs compile. It does not prove Play approval, Defender/SmartScreen
reputation, Accessibility policy acceptance, real-device behavior, or model
quality. Those claims require the platform evidence matrix in
[`docs/release/README.md`](../release/README.md).
